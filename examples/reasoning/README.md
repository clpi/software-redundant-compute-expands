# Incremental Horn reasoning, measured against Vampire, E, Z3 and cvc5

`horn.py` and its native build `native/horn.c` decide function-free Horn clause sets without
equality (TPTP class CNF EPR HRN) by semi-naive forward chaining over one append-only clause
log: each new fact is joined only through the rule positions it can fill, so a clause appended
later costs only the derivations it enables. Argument indexes are built only for positions a
join looks up. A refutation is printed as its derivation DAG (`--proof-json`) and re-checked by
`check.py`, which has its own matcher.

`bench/bench.py` runs every solver as its own process on the same problem with the same wall
limit and keeps each solver's full output under its sha256. Peak memory comes from `wait4` in a
tiny fork shim (`bench/memrun.c`), because a forked child inherits its parent's peak resident
size across exec. `bench/table.py` summarizes; `bench/incr.py` is the incremental benchmark
(an answer after every appended clause).

## Measured (receipts in the project files, `reasoning/receipts-hrn254`)

254 TPTP v9.0.0 problems of class CNF_UNS_EPR_NEQ_HRN, 30 s wall limit, runs in parallel on
4 cores. Vampire 5.1.2 (casc mode), E 3.5.12 (--auto), Z3 and cvc5 1.4.2 (cvc5 with
full-saturate-quant) on an SMT-LIB translation. Native at the commit that saturates once every
clause is in (the first run saturated after each clause; see below).

| solver | solved | median wall* | total wall* | median peak memory* |
|---|---|---|---|---|
| native | 242 | 5.9 ms | 6.3 s | 2.9 MB |
| Vampire | 247 | 12.3 ms | 12.3 s | 9.3 MB |
| E | 242 | 20.5 ms | 13.4 s | 7.4 MB |
| Z3 | 236 | 33.8 ms | 19.7 s | 36.3 MB |
| cvc5 | 230 | 144.4 ms | 182.2 s | 48.8 MB |

\* on the 230 problems every solver solved. Head to head with Vampire on the 242 both solve:
native is faster on 231 and uses less memory on 235. Native solves everything Z3 and cvc5 solve.

Losses, open: Vampire solves 5 that native does not (MSC015-1.025/027/030, PLA031-1.006/007), E 3
(the MSC015 ones). Counters and planning with exponential ground state spaces; Vampire resolves
rules with rules into shortcuts (4,524 resolution steps for a 2^30-step counter). Searching
backward from the planning goal does not collapse it (the backward frontier grows about 2.3x per
step on PLA031-1.005). A saturation core with rule composition and subsumption is the open work
order. Nobody solves PLA031-1.008 or PUZ056-2.015 and up within 30 s.

Fixed on the way: the first native run saturated after every clause, so on the Rubik's cube
problems (PUZ037-2/3) it explored the subgroup generated by the first four moves before the moves
that reach the goal arrived. Saturating once all clauses are in solves them in 0.2 s and 4.1 s.

Proofs: every native refutation is checked by `check.py`, except MSC015-1.022, whose 1 GB proof
(4,194,305 steps) checks when run alone but ran the checker out of memory in the parallel run;
a streaming checker is open.
